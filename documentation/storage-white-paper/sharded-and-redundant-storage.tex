\begin{abstract}
Hedgehog stores a file on the Unigrid Network as many small, encrypted fragments spread over the active
gridnodes. The file survives the loss of a large share of those fragments while its owner is offline, because the
gridnodes repair losses themselves. One random 256-bit secret, the \emph{fingerprint}, both locates and decrypts
the file, and the network keeps no other record of who owns it. Two layers of Reed-Solomon erasure coding divide
the work. An outer layer, whose structure only the owner knows, protects the file against the loss of whole chunks.
An inner layer lets gridnodes verify and rebuild every chunk on their own, without learning, except in short
stripes, which chunks belong together. At default settings a large file costs about 2.3 times its size, a chunk
survives the loss of any 8 of its 24 fragments, and a full stripe of 48 chunks survives the loss of any 16 of them.
Stiftelsen The Unigrid Foundation governs every parameter through a signed \emph{StorageSpork}. Each file records
the layout it was written with, and a format identifier travels with the fingerprint, the manifest and every
fragment, so the network can evolve without breaking what it already holds. This paper describes the design as
implemented, explains the reasons behind it, and analyses its durability, cost and security, including its known
limits.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The Unigrid Network~\cite{unigrid-whitepaper} is built on gridnodes: service nodes that lock collateral and give
the network storage space, communication channels and compute cycles. The idea descends from the masternodes of
Darkcoin~\cite{darkcoin2014}. Hedgehog is the Java implementation of the network's node software. This paper
describes its storage layer: how a file is cut up, encrypted, coded, placed, found again, repaired and deleted, and
what every participant can and cannot learn along the way.

Storing data on machines that strangers run is hard for four reasons:

\begin{itemize}
	\item \textbf{Churn.} Gridnodes join, leave, crash and lose disks. A file must outlive the machines that hold
	      it, and it must do so while its owner is offline. The network therefore has to notice losses and repair them
	      itself, and repair traffic, not disk space, becomes the main cost of keeping data~\cite{blake2003}.
	\item \textbf{Privacy.} Gridnodes are not trusted with content. They must not read a file, and they should not
	      learn how large it is, which pieces belong together, or who stored it.
	\item \textbf{Integrity.} Any gridnode may corrupt, forge or withhold data, or lie about what it holds.
	\item \textbf{Change.} Chunk sizes and redundancy levels will need tuning as the network grows, but files that
	      are already stored must stay readable.
\end{itemize}

Hedgehog meets these demands with a small set of well-understood tools. A file is encrypted with keys derived from
a random secret, coded twice with Reed-Solomon codes~\cite{reed1960}, and spread over the gridnodes by rendezvous
hashing~\cite{thaler1998}. Every stored piece carries a signature and a Merkle proof~\cite{merkle1987}, so anyone
can check it without knowing a secret. Gridnodes watch over the pieces they hold and rebuild lost ones without the
owner. The owner keeps a single string of 50 characters, the fingerprint, and nothing else.

The core of the design is the split of the erasure code into two layers. The owner applies an outer code across
many chunks and keeps its structure to itself. The network applies an inner code within each chunk, and that code
is public. Repair then needs only public information, and it reveals nothing that links chunks into files. Other
systems that erasure-code data across untrusted nodes leave repair to the owner, to a client that holds a
capability for the file, or to a coordinator that knows which pieces form each file
(Section~\ref{sec:related}). Hedgehog needs none of them.

The storage layer is deliberately low level. It stores opaque files and returns a fingerprint; it knows nothing
about names, folders or buckets. An object-storage interface in the style of S3 is planned as a separate layer on
top of it. This paper describes the protocol as implemented in Hedgehog. Every constant in it is the value the
implementation uses at default settings, and Stiftelsen The Unigrid Foundation can change most of them
(Section~\ref{sec:governance}).

Section~\ref{sec:background} introduces the building blocks, and Section~\ref{sec:goals} states the goals, the
trust assumptions and the threat model. Section~\ref{sec:overview} gives an overview of the design and follows one
file through its life. Sections~\ref{sec:keys} to~\ref{sec:versioning} describe the formats: keys, encryption,
coding, fragments, placement and the manifest. Sections~\ref{sec:operations} to~\ref{sec:protocol} describe the
operations, ownership, repair, quotas, governance and the wire protocol. Sections~\ref{sec:analysis}
and~\ref{sec:security} analyse durability, cost, performance and security. Section~\ref{sec:related} compares the
design with related systems, and Section~\ref{sec:future} lists future work.

\section{Building blocks}
\label{sec:background}

The design combines a few standard building blocks. This section explains each one as far as the rest of the paper
needs it. Readers who know them can skip ahead.

\subsection{Erasure codes}

An erasure code turns $k$ data shards into $n = k + m$ shards, such that a subset of them rebuilds the data. A code
is \emph{maximum distance separable} (MDS) when any $k$ of the $n$ shards suffice. It then tolerates the loss of any
$m$ shards, which is the most that any code with the same overhead can tolerate~\cite{macwilliams1977}. A code is
\emph{systematic} when its first $k$ shards are the data itself, so intact data is read without decoding.
Reed-Solomon codes~\cite{reed1960} are the classic MDS codes. RAID protects disk arrays with
parity~\cite{patterson1988}, Reed-Solomon codes extend that protection to any number of parity
shards~\cite{plank1997}, and information dispersal applies the same idea across machines~\cite{rabin1989}.

Replication is the simplest alternative. Three copies cost three times the data and survive the loss of any two. A
code with $k = 16$ and $m = 8$ costs 1.5 times the data and survives the loss of any eight shards. For the same
overhead, erasure codes are far more durable than replication~\cite{weatherspoon2002}. The price is paid at repair:
to rebuild one lost shard, a node must read $k$ others. In a network with churn, repair traffic therefore dominates
the cost of redundancy~\cite{blake2003,dimakis2010}, and how much of the advantage survives depends on how
available and how stable the nodes are~\cite{rodrigues2005}. Hedgehog repairs only when losses pass a threshold
(Section~\ref{sec:repair}).

\subsection{Finite fields}

Reed-Solomon codes compute on bytes as elements of the finite field $\mathrm{GF}(2^8)$~\cite{macwilliams1977}. The
field has 256 elements, one for each byte value. Addition is bitwise XOR, so subtraction is the same operation.
Multiplication is multiplication of polynomials with binary coefficients, reduced modulo a fixed irreducible
polynomial of degree 8, and every element except zero has an inverse. Software multiplies through tables of
logarithms and exponents~\cite{rizzo1997,plank1997}, as the RAID-6 code in Linux does~\cite{anvin2004}.

\subsection{Authenticated encryption}

AES-256-GCM~\cite{fips197,sp80038d,mcgrew2004} is authenticated encryption with associated
data~\cite{rogaway2002}. It encrypts a plaintext under a key and a 12-byte nonce, and adds a 16-byte tag. The tag
authenticates the ciphertext together with \emph{additional data}, which is not encrypted; in Hedgehog it is never
stored at all, because both sides compute it. A change to either makes decryption fail. GCM demands that a nonce
never repeats under one key: a repeat reveals the XOR of two plaintexts and lets an attacker forge
tags~\cite{joux2006}.

\subsection{Key derivation}

HKDF~\cite{rfc5869,krawczyk2010} derives any number of keys from one secret. Each key is bound to an \emph{info}
label, and keys with different labels are independent: knowing some of them reveals nothing about the others or
about the secret.

\subsection{Signatures and self-certifying names}

Ed25519~\cite{rfc8032,bernstein2012} is a signature scheme with 32-byte public keys and 64-byte signatures. Its
private key is a 32-byte seed, so a key pair can be derived from a secret instead of being stored. When an object is
named by the hash of a public key, anyone can check that a signed statement about the object comes from the holder
of the private key. No certificate authority or directory is involved. Such a name is
\emph{self-certifying}~\cite{mazieres1999}.

\subsection{Merkle trees}

A Merkle tree~\cite{merkle1987} commits to a list of items with one hash, the \emph{root}. Each leaf is the hash of
one item, and each inner node is the hash of its two children. The \emph{proof} for one item is the list of sibling
hashes on the path from its leaf to the root, $\lceil \log_2 n \rceil$ hashes for $n$ items. Anyone who trusts the
root can check an item against it. Distinct prefixes for leaves and inner nodes stop an inner node from passing as a
leaf~\cite{rfc6962,rfc9162}.

\subsection{Rendezvous hashing}

Rendezvous hashing, also called highest random weight hashing~\cite{thaler1998}, maps an object to nodes without a
directory. Every node gets a score, the hash of the object's name together with the node's name, and the object
belongs to the nodes with the highest scores. Everyone who knows the same list of nodes computes the same answer.
When a node joins or leaves, only the objects for which it scores high are affected. This is the same small
disruption that consistent hashing offers~\cite{karger1997}, without its ring and without the routing tables of a
distributed hash table~\cite{maymounkov2002}.

\section{Goals, trust and threat model}
\label{sec:goals}

The design has six goals:

\begin{enumerate}
	\item \textbf{Durability.} A file survives gridnode churn and disk loss while its owner is offline, because
	      gridnodes repair lost fragments themselves.
	\item \textbf{Confidentiality.} Only the fingerprint holder can read the file.
	\item \textbf{Unlinkability.} No gridnode, repairer or holder of stored data can tell which fragments form a
	      file or how large the file is, and nothing stored ties a fragment to its uploader. Two items are
	      \emph{unlinkable} when an observer cannot tell whether they are related any better than it could without
	      seeing them~\cite{pfitzmann2010}.
	\item \textbf{Self-verification.} Anyone can check that a fragment is genuine without knowing a secret.
	\item \textbf{Governance.} The foundation tunes the network through one signed spork, and every file keeps the
	      layout it was written with.
	\item \textbf{Evolvability.} A format identifier travels with the fingerprint, the manifest and every fragment,
	      so a later format can live beside the current one.
\end{enumerate}

\subsection{Trust}

The design trusts three kinds of party, each for a different purpose:

\begin{description}
	\item[The owner's node.] A user stores and reads files through the REST interface of their own Hedgehog node,
	      which listens on localhost by default. That node sees the plaintext and the fingerprint. It is the user's own
	      software and is trusted like any other program that handles the file.
	\item[Gridnodes.] Gridnodes store, check and repair fragments. None of them is trusted: each may be curious,
	      lazy or malicious. Gridnodes lock collateral~\cite{unigrid-whitepaper}, which makes large numbers of them
	      expensive to run and so limits Sybil attacks~\cite{douceur2002}. Section~\ref{sec:durability} shows how
	      many losses the design tolerates.
	\item[Stiftelsen The Unigrid Foundation.] The foundation signs the StorageSpork. Its key plays no part in encryption,
	      placement or deletion. It sets the parameters of new uploads, but it cannot read, find or delete a file.
\end{description}

Five terms recur through this paper:

\begin{description}
	\item[Chunk] A fixed-size piece of 1\,MiB by default. Data chunks carry encrypted file bytes; parity chunks come
	      from the outer code.
	\item[Stripe] A run of up to 32 data chunks together with their outer parity chunks. Only the owner knows which
	      chunks form a stripe.
	\item[Group] One chunk as the network sees it, named by a 32-byte group identifier.
	\item[Fragment] One inner-code piece of a group, 64\,KiB by default, and the unit a gridnode stores.
	\item[Window] The $W$ gridnodes that rank highest for a group, 40 by default. A group's fragments live in its
	      window, and a gridnode that stores one of them is a \emph{holder} of the group.
\end{description}

The split into two layers is the core of the design. The owner applies the outer code across whole chunks and keeps
the grouping to itself. Gridnodes see only single chunks, each coded again into fragments that they can rebuild on
their own. A repairer therefore holds at most one chunk of ciphertext, and, apart from the short stripes of
Section~\ref{sec:security}, nothing in the group tells it which other chunks belong to the same file
(Figure~\ref{fig:layers}).

\subsection{Why two layers}
\label{sec:why-two}

The two layers resolve a tension between repair and privacy. For the network to repair a file without its owner,
gridnodes must know which pieces belong together. For the network to learn nothing, they must not. Hedgehog lets
gridnodes know the members of one chunk and, apart from the limits of Section~\ref{sec:security}, nothing beyond
it. The alternatives each give up one of the goals:

\begin{itemize}
	\item \textbf{One code across the file.} If the network held the fragments of a single code spanning many
	      chunks, repairers would have to know which fragments form a codeword, which is exactly the link the design
	      hides. Every repair would also read many chunks' worth of data.
	\item \textbf{The inner code alone.} Gridnodes could still repair each chunk, but each chunk would be only as
	      safe as its own group. A group that loses more than 8 of its 24 fragments between two repairs is gone, and
	      the file with it. The outer code covers exactly this case. It adds no names or placement that tie groups
	      together, because only the owner applies and reads it; Section~\ref{sec:security} describes what its
	      content still reveals in short stripes.
	\item \textbf{Replication.} Three copies of every chunk cost 3 times the file. A stripe stored that way is still
	      lost far more often than with both layers at 2.25 times (Section~\ref{sec:durability}).
	\item \textbf{Repair by the owner.} An owner who checks and rebuilds their own files must stay online, which
	      breaks the first goal.
	\item \textbf{A trusted coordinator.} A service that knows every file's structure and directs repair is a
	      central point of trust and of failure, and it learns what the design hides from everyone else.
\end{itemize}

Coding at two levels is an old idea. Product codes~\cite{elias1954} and concatenated codes~\cite{forney1966}
combine an inner and an outer code, and large storage systems code at two levels to keep most repairs
local~\cite{huang2012,muralidhar2014}. Hedgehog adds a new reason for the split: the two layers separate what the
owner knows from what the network needs.

\subsection{Designs not taken}

Three other families of techniques were considered and set aside:

\begin{itemize}
	\item \textbf{Fountain codes and network coding.} Rateless fountain codes~\cite{luby2002,mackay2005} and network
	      coding for repair~\cite{dimakis2010} create new coded pieces on demand. A piece that did not exist at upload
	      is not covered by the owner's signature, so a gridnode cannot tell a genuine piece from a polluted one
	      without far heavier tools, such as homomorphic signatures~\cite{boneh2009}. Hedgehog fixes all $n_{max}$
	      fragments of a group at upload and commits to every one of them.
	\item \textbf{Entanglement codes.} Entanglement codes~\cite{estrada2018} tie each new block to blocks stored
	      before it, in a global order. That order conflicts with deletion and with per-node quotas.
	\item \textbf{Deduplication.} Convergent encryption~\cite{douceur2002b} lets identical files share storage, but
	      it tells anyone who holds a copy of a file whether the file is stored~\cite{harnik2010}. A fresh random
	      fingerprint for every upload rules this out: two uploads of the same file share nothing.
\end{itemize}

\subsection{The life of a file}
\label{sec:life}

Consider a file of 100\,MiB, stored at default settings (Table~\ref{tab:life}).

\begin{enumerate}
	\item The owner's node draws a fresh fingerprint and derives every key from it.
	\item It reads the file in pieces of 1\,048\,560 bytes and seals each into a data chunk of exactly 1\,MiB. That
	      gives 101 data chunks; the last one holds the remaining 1\,600 bytes and padding.
	\item It groups the chunks into four stripes of 32, 32, 32 and 5 data chunks, and adds 16, 16, 16 and 3 outer
	      parity chunks.
	\item Each of the 152 chunks becomes a group with its own key pair. Its 1\,MiB is cut into 16 fragments of
	      64\,KiB and coded into 32: the 16 data fragments, 8 guaranteed parity fragments and 8 extra ones.
	\item The 24 guaranteed fragments of each group go to 24 different gridnodes chosen by rendezvous hashing, and
	      the 8 extras to spare gridnodes, which keep them in their pool of extras.
	\item Three copies of an encrypted manifest record the file size and the layout, as three more groups.
\end{enumerate}

\centering

\begin{tabular}{@{}lr@{}}

\midrule
Data chunks & 101 \\

Outer parity chunks & $16 + 16 + 16 + 3 = 51$ \\

Guaranteed fragments & 3\,720 \\

The file thus becomes 155 groups that look unrelated, with 3\,720 guaranteed fragments between them. With 1\,000
active gridnodes, each gridnode holds on average about four of the file's guaranteed fragments and one extra, never
two of the same group.

To read the file, a node derives the manifest's group identifiers from the fingerprint, collects 16 fragments of one
manifest copy, and learns the size and the layout. It then derives the identifiers of the 101 data groups and
fetches 16 verified fragments of each. Parity groups are fetched only when a data group is missing.

While the file is stored, gridnodes come and go. Every hour, one holder of each group may be on duty to count the
fragments that remain, and once the group is down to 20 fragments, 4 more than it needs, the holder on duty rebuilds
the missing ones from the others. When the owner deletes the file, the node signs one delete per group with the
group's private key and sends it to the group's window. The gridnodes drop their fragments and keep the signed proof
for 30 days, so that stale copies are dropped instead of repaired.

\section{The fingerprint and its keys}
\label{sec:keys}

The fingerprint is the only input retrieval needs. Every address and key the network uses for a file is derived
from it (Figure~\ref{fig:keys}), and nothing else about the file is stored anywhere.

\subsection{The fingerprint}

The secret is 32 bytes from a cryptographically secure random generator, drawn fresh for every upload. Users see it
as Base58Check text~\cite{base58check}: the format identifier as version byte, the secret, and a 4-byte checksum,
the first four bytes of a double SHA-256 hash~\cite{fips1804}. These 37 bytes are written as 50 Base58 characters,
an alphabet that leaves out characters that are easy to confuse, such as \code{0}, \code{O}, \code{I} and \code{l}. The
implementation uses the Base58 codec of bitcoinj~\cite{bitcoinj}. Parsing trims the text, verifies the checksum,
requires exactly 33 decoded bytes, and requires a known format identifier. A mistyped character fails the checksum,
except with probability $2^{-32}$, so a typo is rejected before any network traffic.

Guessing is hopeless. Even $2^{80}$ guesses against $2^{40}$ stored files find one of them with probability about
$2^{-136}$.

\subsection{Derived keys}

Every key comes from HKDF-SHA256 over the secret. The salt, \code{"hedgehog-storage-v1"}, names the format, and
every output is 32 bytes long. The implementation uses the HKDF and Ed25519 code of Bouncy

\begin{equation}
	K_{\mathit{label}} = \mathrm{HKDF\text{-}SHA256}(\mathit{IKM} = \mathit{secret},\ \mathit{salt},\ \mathit{info}
	= \mathit{label},\ L = 32)
\end{equation}

\subsection{Group identifiers}

Each seed is used directly as an RFC~8032 Ed25519 private key. The 32-byte public key is hashed to name the group:
\begin{equation}
	\mathit{groupId} = \mathrm{SHA\text{-}256}(\mathit{publicKey})
\end{equation}

The group identifier is a self-certifying name~\cite{mazieres1999}. Anyone who meets a public key can check that it
belongs to a group by hashing it, and a signature under that key can only come from the fingerprint holder, who
alone can derive the private key. The identifier names the group in placement, in requests and replies, and on
disk.

Every seed comes from its own HKDF expansion under a distinct label. Without the secret, two group identifiers of
one file are indistinguishable from identifiers of two unrelated files, and nothing in an identifier reveals a
stripe, an index or a file size. This is what keeps the network from linking chunks by their names;
Section~\ref{sec:security} describes the links that the content of short stripes still allows.

Other systems also hand out one string that both locates and decrypts a file, among them Freenet~\cite{clarke2001}
and Tahoe-LAFS~\cite{wilcox2008}. The Hedgehog fingerprint is random rather than derived from the content, so
storing the same file twice produces two unrelated sets of groups.

\section{Encryption}
\label{sec:encryption}

Every data chunk and every manifest copy is AES-256-GCM ciphertext of exactly \code{chunkSize} bytes. Outer parity
chunks are Reed-Solomon combinations of data chunks and have the same size. No stored piece therefore reveals its
content or its position in a file, and none reveals the file's size.

The chunk sequence is a global chunk number, $\mathit{stripe} \cdot \mathit{maxOuterDataChunks} + i$. Each upload
draws a fresh fingerprint and therefore fresh keys, and within one file every data chunk has its own sequence number
and every manifest copy its own copy number. A nonce therefore never repeats under one key. The last four bytes of
the nonce, 0 for chunks and 1 for manifests, separate the two uses once more, although their keys already differ.

\paragraph{Uniform size.} With the defaults a data chunk carries 1\,048\,560 bytes of file data, and the 16-byte
tag fills it to exactly 1\,MiB. The manifest is padded to the same size. A manifest group looks exactly like a data
group, and the last chunk of a file looks like any other.

\paragraph{Tamper resistance.} The sequence number sits in both the nonce and the additional data. A chunk moved to
another position, or taken from another file, fails authentication. The manifest's file size fixes the number of
data chunks, so truncation is detected. Corrupt fragments are usually rejected earlier by their Merkle proof. A
chunk that still fails authentication stops retrieval with a data-loss error, never with wrong output.

\paragraph{Parity.} Outer parity chunks are Reed-Solomon combinations of ciphertext chunks and are not encrypted
again. Each one on its own looks as random as the ciphertext it comes from, and it carries no sequence number.
Together with the data chunks of its stripe, though, it satisfies the equations of the outer code;
Section~\ref{sec:security} discusses what that reveals.

\paragraph{Encrypt, then disperse.} Encrypting before coding follows Krawczyk's secret sharing made
short~\cite{krawczyk1993} and AONT-RS~\cite{resch2011}: the data is made unreadable first, and the code then spreads
ciphertext. Those schemes also disperse the key, so that any $k$ pieces reveal the data to whoever collects them.
Hedgehog keeps the key out of the network altogether: it exists only in the fingerprint.

\subsection{Why the layer does not compress}

The storage layer does not compress, and this is a deliberate choice.

\begin{itemize}
	\item \textbf{Ciphertext does not compress.} Everything that reaches a gridnode is ciphertext or parity computed
	      from ciphertext, which looks random.
	\item \textbf{Compression before encryption leaks.} The compressed length depends on the content, and attacks
	      of the CRIME and BREACH family recover secrets from exactly that
	      signal~\cite{kelsey2002,rizzo2012,gluck2013}.
	\item \textbf{Uniform chunks are the privacy mechanism.} Every chunk is padded to the same size, so a compressed
	      file would still occupy whole chunks and hide nothing more.
\end{itemize}

An application that knows its data is compressible, and that its length is not sensitive, can compress before
upload. The layer above storage is the right place for that decision, not the storage format.

\section{Erasure coding}
\label{sec:coding}

Both layers use one systematic Reed-Solomon code over $\mathrm{GF}(2^8)$ whose parity rows form a Cauchy matrix:
any $k$ of the $k + m$ shards rebuild the data. A systematic code whose parity block is a Cauchy matrix is a
generalized Reed-Solomon code~\cite{roth1985}. The Cauchy Reed-Solomon codes of Bl\"omer et
al.~\cite{blomer1995} and of Plank and Xu~\cite{plank2006} build on the same kind of matrix but turn every
multiplication into XORs of bit matrices; Hedgehog multiplies bytes through tables instead. The implementation has
no external dependency.

\subsection{The field}

Bytes are elements of $\mathrm{GF}(2^8)$ with the reducing polynomial $x^8 + x^4 + x^3 + x^2 + 1$ (\code{0x11D})
and generator 2, the choice of RAID-6~\cite{anvin2004}. Addition is XOR. Multiplication uses a precomputed
$256 \times 256$ product table of 64\,KiB beside the usual exponent and logarithm tables, and the inverse is
$\mathrm{EXP}[255 - \mathrm{LOG}[a]]$.

\subsection{The encoding matrix}

The code is linear: every shard is a combination of the data shards, and the $n \times k$ \emph{generator matrix}
says which. Its first $k$ rows are the identity, because the code is systematic, so the $k$ data shards pass through
unchanged. Parity row $r$, for $0 \le r < m$, combines them with a Cauchy matrix:
\begin{equation}
	p_r = \bigoplus_{c=0}^{k-1} C_{r,c} \cdot d_c, \qquad C_{r,c} = \frac{1}{(k + r) \oplus c}
\end{equation}

The row values $k, \dots, k+m-1$ and the column values $0, \dots, k-1$ never overlap, so no denominator is zero.
Every square submatrix of a Cauchy matrix is invertible~\cite{blomer1995,roth1989,macwilliams1977}. Losing shards
deletes rows of the generator matrix, and any $k$ rows that remain still form an invertible matrix
(Figure~\ref{fig:matrix}). The code is therefore MDS: \emph{any} $k$ shards suffice. A careless systematic
construction does not always have this property~\cite{plank2005}; the Cauchy construction has it by design. The
implementation allows at most 255 shards per code.

\paragraph{Prefix property.} A parity row depends only on its absolute position $k + r$, never on $m$. The parity of
$\mathrm{RS}(k, m_1)$ is therefore the first $m_1$ rows of $\mathrm{RS}(k, m_2)$. The inner layer relies on this:
each chunk is encoded once to $n_{max}$ fragments. Fragments $0$ to $n_{in} - 1$ are exactly the guaranteed code,
and the rest are extra parity that gridnodes may keep or drop without touching the guaranteed fragments.

\subsection{Worked example}

Take $k = 2$ and $m = 1$. The single parity row is $C = (1/2,\ 1/3)$. In this field $1/2 = \mathtt{0x8E}$ and
$1/3 = \mathtt{0xF4}$, so each parity byte is
\begin{equation}
	p = \mathtt{0x8E} \cdot d_0 \oplus \mathtt{0xF4} \cdot d_1 .
\end{equation}
If $d_0$ is lost, one multiplication by 2, the inverse of \code{0x8E}, restores it:
\begin{equation}
	d_0 = 2 \cdot (p \oplus \mathtt{0xF4} \cdot d_1) .
\end{equation}

\subsection{Decoding}

The decoder takes the first $k$ present shards, builds their $k \times k$ submatrix and inverts it by Gauss-Jordan
elimination over $\mathrm{GF}(2^8)$ in $O(k^3)$. It multiplies the inverse by the shards to recover the data in
$O(k^2 L)$ for shard length $L$, and then re-encodes all parity shards, whether they were missing or not. Retrieval
skips the outer decode when every data chunk arrived.

\subsection{Layout}
\label{sec:layout}

With $\mathrm{pct}(v, p) = \lceil v \cdot p / 100 \rceil$ and $M = \mathit{maxOuterDataChunks}$, a file of
$\mathit{fileSize}$ bytes is laid out as follows:
\begin{align}
	\mathit{payload} &= \mathit{chunkSize} - 16 & D &= \max\left(1, \left\lceil \mathit{fileSize} / \mathit{payload}
	\right\rceil\right) \\
	S &= \left\lceil D / M \right\rceil & k_s &= \min(M,\ D - s \cdot M) \\
	m_s &= \mathrm{pct}(k_s, \mathit{outerParity}) & k_{in} &= \mathit{chunkSize} / \mathit{fragmentSize} \\
	m_{in} &= \mathrm{pct}(k_{in}, \mathit{innerParity}) & n_{in} &= k_{in} + m_{in} \\
	n_{max} &= k_{in} + \mathrm{pct}(k_{in}, \mathit{maxParity}) & W &= n_{max} + \mathit{placementSlack}
\end{align}

\subsection{How the layers combine}

A group is lost only when more than 8 of its 24 guaranteed fragments are gone, or more than 16 of 32 when all
extras are held. A lost group is one erasure for the outer code, and a full stripe is lost only when more than 16 of
its 48 groups are lost. The inner code thus turns fragment losses into rare group losses, and the outer code
corrects those. Because both codes are linear, the two layers together form a product code~\cite{elias1954}: the
fragments of an outer parity group are the same outer combination of the stripe's data fragments, index by index.
Section~\ref{sec:durability} puts numbers on the protection this gives.

\section{Verifiable fragments}
\label{sec:fragments}

Every fragment carries everything needed to check it, so any gridnode can reject forged or corrupt data without a
secret. OceanStore made the fragments of its archive self-verifying in a similar way~\cite{kubiatowicz2000}.

\subsection{The group descriptor}

The uploader signs a 136-byte descriptor for each group with the group's private key (Figure~\ref{fig:descriptor}).
The signature covers the ASCII domain \code{"hh-group-v1"} followed by the first 72 descriptor bytes, an 83-byte
message. Because only the fingerprint holder can derive the private key whose public key hashes to the group
identifier, a valid descriptor proves that the group comes from the owner.

\subsection{The Merkle tree}

The root commits to all $n_{max}$ fragment slots, extras included. Leaves are padded to a power of two, so the tree
has depth $\lceil \log_2 n_{max} \rceil$: 5 with the defaults and at most 8. Distinct tags separate the three kinds
of node; the leaf and node tags are those of Certificate Transparency~\cite{rfc6962}:
\begin{align}
	\mathit{leaf}_i &= \mathrm{SHA\text{-}256}(\mathtt{0x00} \cat \mathrm{u8}\ i \cat \mathit{data}_i) \\
	\mathit{node} &= \mathrm{SHA\text{-}256}(\mathtt{0x01} \cat \mathit{left} \cat \mathit{right}) \\
	\mathit{empty} &= \mathrm{SHA\text{-}256}(\mathtt{0x02})
\end{align}

The index is part of each leaf, so a fragment cannot pass as another slot of its group. Figure~\ref{fig:merkle}

Committing to every slot, extras included, has two effects. Extra fragments verify like any other. And a repairer
that rebuilds fragments must recompute the whole tree and arrive at the signed root. The rebuilt fragments then
carry valid proofs although the repairer never holds the owner's key, and a repairer cannot produce any fragment
the owner did not commit to.

\subsection{The fragment}

A fragment on the wire is the descriptor, its index, the sibling hashes from leaf to root, and the data:
\begin{multline}
	\mathit{descriptor}_{[136]} \cat \mathrm{u8}\ \mathit{index} \cat \mathrm{u8}\ \mathit{proofLen} \\
	\cat \mathit{proof}_{[32 \cdot \mathit{proofLen}]} \cat \mathrm{u32}\ \mathit{dataLen} \cat \mathit{data}
\end{multline}
With the defaults that is 65\,838 bytes, of which 302 are overhead. Decoding requires the data length to match the
bytes that remain. A receiver then checks, in order:

\begin{enumerate}
	\item the descriptor is well formed: $1 \le k_{in}$, $k_{in} + m_{in} \le n_{max} \le 255$, positive fragment
	      size;
	\item $\mathrm{SHA\text{-}256}(\mathit{publicKey})$ equals the group identifier: for a fetched fragment the one
	      that was requested, while a stored fragment names its group through its own key;
	\item the data length equals the descriptor's fragment size;
	\item the descriptor signature verifies;
	\item the index is a slot of the group, the proof has the depth of the tree, and it leads from the fragment to
	      the signed root.
\end{enumerate}

A fetched fragment must also carry the format that the fingerprint names, and a gridnode stores a fragment only when
its size is within a factor of 16 of the current spork's (Section~\ref{sec:repair}). A group therefore cannot be
forged without its private key, and any altered byte is detected by anyone.

\section{Placement}
\label{sec:placement}

Fragments go to active gridnodes chosen by rendezvous hashing~\cite{thaler1998}, so any node can compute where a
group lives without a directory service.

\begin{enumerate}
	\item Score every active gridnode as $\mathrm{SHA\text{-}256}(\mathit{groupId} \cat \mathit{gridnodeId})$ and sort
	      the scores in descending order, breaking ties by gridnode identifier. The first $W$ entries form the
	      group's window.
	\item Guaranteed fragment $i$ goes to window rank $i$, for $i < n_{in}$.
	\item Ranks $n_{in}$ to $W - 1$ are spares. When a guaranteed store fails, for any reason, the next spare is
	      tried.
	\item Extra fragments go to the spares that remain, without waiting for an answer.
\end{enumerate}

\caption{One group's ranking of the active gridnodes by $\mathrm{SHA\text{-}256}(\mathit{groupId} \cat
\mathit{gridnodeId})$, highest first, as an upload places it when every gridnode accepts. Gridnodes beyond rank 39

\label{fig:window}

A gridnode holds at most one fragment of any group; it answers \code{DUPLICATE} to a second one. Rendezvous hashing
needs nothing but the list of active gridnodes, which every Hedgehog node already has, and ranking costs one SHA-256
hash per active gridnode and group. It gives every group its own pseudo-random order of gridnodes, so the groups of
one file land on unrelated sets of gridnodes, and a gridnode's rank in one window says nothing about its rank in
another.

Churn moves little. When a gridnode joins and ranks inside a window, every member below it moves down one rank, and
only the holder pushed out of the window moves its fragment back inside (Section~\ref{sec:repair}). When a gridnode
leaves, nothing moves: its fragments are simply missing, and repair rebuilds them once the threshold is reached.

Placement is only as consistent as the nodes' views of the active gridnodes. An upload takes one snapshot of that
view and uses it for all its groups. Two nodes whose views differ by a few gridnodes compute windows that differ in a
few ranks. The spare ranks absorb such differences: retrieval asks the rest of the window when the top ranks fall
short, and relocation moves fragments into the window that the current view defines. When the uploader's own node
is itself a gridnode in the window, it serves its share in-process rather than over the network.

\section{Manifest and format versioning}
\label{sec:versioning}

\subsection{The manifest}

The manifest is 26 bytes of plaintext, padded and encrypted to one full chunk (Figure~\ref{fig:manifest}). It is
the one piece a file cannot do without: without it, a reader knows neither the size nor the layout. It is therefore
stored \code{manifestCopies} times, 3 by default and at most 16. Each copy is an independent group with its own key
and its own ranking of gridnodes; in a small network the windows of different copies share many gridnodes. Swarm
solves the same problem for the root chunks of its files, which its erasure code cannot protect, by storing
dispersed replicas of them~\cite{swarm2024}.
Retrieval accepts a manifest only if it decrypts, its layout is valid, and its format matches the fingerprint's.

\centering

	\bitheader{0-9} \\
	\bitbox{1}{\scriptsize fmt} & \bitbox{8}{fileSize (u64)} & \bitbox{1}{\scriptsize copies} \\
	\bitbox{4}{chunkSize (u32)} & \bitbox{4}{fragmentSize (u32)} & \bitbox{2}{\scriptsize outer\,\%} \\
	\bitbox{2}{\scriptsize maxOuter} & \bitbox{2}{\scriptsize inner\,\%} & \bitbox{2}{\scriptsize maxParity\,\%} &
	\bitbox[]{4}{}
\end{bytefield}
\caption{Manifest plaintext, 26 bytes, big-endian.}
\label{fig:manifest}
\end{figure}

The manifest records the copy count, so that a delete can withdraw every copy. The field is one byte, so the format
allows up to 255 copies; the spork caps the count at 16.

The foundation may change chunk size, parity or window at any time. An old file is still read with the layout in
its manifest. The current spork still supplies the placement slack, both for the manifest search and for the windows
of the file's groups, and the manifest search covers every copy count the spork can name
(Section~\ref{sec:operations}).

apart:

A gridnode that finds a fragment file of an unknown format at startup leaves it on disk, untouched and uncounted, so

have fixed layouts, and the delete message is signed under the versioned domain \code{"hh-delete-v1"}, so a later
format can add a format byte to either.

\section{Storing, retrieving and deleting}
\label{sec:operations}

\subsection{Store}

\begin{enumerate}
	\item Require a valid StorageSpork and at least $n_{in}$ active gridnodes; otherwise fail before sending anything.
	      The upload uses one snapshot of the active gridnodes throughout.
	\item Draw a fresh fingerprint.
	\item Read the input one stripe at a time, so memory stays bounded to one stripe. An empty file becomes one
	      padded chunk, so every file has a first stripe to find.
	\item Encrypt the data chunks of the stripe and compute its outer parity chunks.
	\item Place the stripe's groups one by one, in an order shuffled with a secure random generator. For each group,
	      encode it to $n_{max}$ fragments, build its Merkle tree and sign its descriptor. Send the guaranteed
	      fragments to ranks $0$ to $n_{in} - 1$ in shuffled order, each delayed by a random 0 to 25\,ms. Wait for
	      every answer, and retry each refusal on the remaining spares, one after another. The group fails when fewer
	      than $n_{in}$ window members accept it. Once the guaranteed fragments are in place, send the extras to the
	      spares that are left, in the same shuffled and delayed way, and do not wait for their answers.
	\item After the last stripe, store the manifest copies as ordinary groups.
	\item On any failure, send \code{DELETE\_GROUP} for every group placed so far, the failed one included, then
	      report the error. A failed upload thus leaves no live group behind, unless the node stops before its
	      rollback (Section~\ref{sec:security}).
\end{enumerate}

The shuffled order and the delays make it harder for a gridnode to read a stripe's structure off the order and
timing in which its fragments arrive.

\subsection{Retrieve}

Retrieval starts from the fingerprint alone:

\begin{enumerate}
	\item Derive the manifest group keys and their identifiers, and find a manifest with the two-pass search below.
	\item Decrypt the manifest. It gives the file size and the layout the file was written with. The data groups
	      use the window $n_{max} + \mathit{placementSlack}$, with $n_{max}$ from the manifest and the slack from the
	      current spork.
	\item For each data group, derive its identifier from its stripe and index, and ask the $k_{in} + 2$
	      top-ranked gridnodes of its window in parallel, 18 with the defaults. The round ends as soon as $k_{in}$
	      verified fragments with distinct indices are in. If fewer arrive, ask the rest of the window once every
	      answer is in or has timed out.
	\item Decode each group with the inner code. Fetch a stripe's parity groups only while a data group is missing,
	      and rebuild the missing chunks with the outer code.
	\item Decrypt, write out, and cut the output to the file size.
\end{enumerate}

Asking two more gridnodes than needed lets a read finish without waiting for the slowest answers, a standard remedy
for tail latency~\cite{dean2013}; OceanStore read its archive the same way~\cite{kubiatowicz2000}.

The manifest search runs in two passes, because the spork may have changed since the upload. The narrow pass looks
for copies 0 to 15, the highest count the spork allows, in the current placement window of 40 gridnodes. The wide
pass looks for the copies the current spork names across $255 + \mathit{slack}$ gridnodes, 263 with the defaults.

A wrong fingerprint and a fully lost file give the same answer: \emph{not found}. This is deliberate: the network
cannot confirm that a guessed fingerprint exists. It is also the slowest answer. The search asks for up to 16
copies in the narrow pass and 3 in the wide one, and every round in which a window member stays silent waits for
the 10-second request timeout, so rejecting a wrong fingerprint can take minutes.

An HTTP answer commits to its status before its body. The first stripe is therefore recovered in full before any
output starts, so a file whose beginning is lost is reported as lost at once, not after a partial transfer. A stripe
that is lost further in cuts the answer short; the command-line client catches this by comparing the length it
received with the announced size.

\subsection{Delete}

Delete needs only the manifest, so even a file with lost data can be deleted. For every data, parity and manifest
group, it sends a signed \code{DELETE\_GROUP} to the whole window and waits for the answers. Failed answers are
ignored: holders that missed the delete learn of it from the tombstones of the others
(Section~\ref{sec:ownership}).

\section{Ownership and deletion}
\label{sec:ownership}

The network keeps no owner record: whoever holds the fingerprint owns the file. There are no accounts, no uploader
signatures and no per-user index. A gridnode sees which Hedgehog node sent it a fragment, but it stores nothing that
ties the fragment to that node. The fingerprint works like a capability~\cite{wilcox2008}: holding it is the right
to act, and ownership gives two powers, both through keys derived from it:

\begin{itemize}
	\item \textbf{Read.} Only the fingerprint yields the manifest key and the chunk key.
	\item \textbf{Delete.} Only the fingerprint yields the private key of each group, and only that key signs a
	      valid delete.
\end{itemize}

\subsection{The delete proof}

A delete is one \code{DELETE\_GROUP} packet per group, sent to every gridnode in that group's window. It carries the
group's public key, a timestamp in epoch milliseconds, and an Ed25519 signature over a 52-byte message:
\begin{equation}
	m = \texttt{"hh-delete-v1"} \cat \mathit{groupId}_{[32]} \cat \mathit{timestamp}_{\mathrm{i64}}
\end{equation}

A gridnode accepts the delete only if the public key hashes to the group identifier and the signature verifies. The
proof is \emph{self-certifying}: it needs no stored state to check. Even a gridnode that does not hold the group can
verify it and keep it as a tombstone.

\centering
\small
\begin{tabular}{@{}ll@{}}

\midrule

The tombstone cannot be written & \code{ERROR} \\
Otherwise: tombstone written, any held fragment removed & \code{OK} \\
\bottomrule

\end{table}

The signed timestamp is kept with the proof but not checked for freshness. A replayed proof can only repeat a delete
the owner has already signed, and since every upload draws a fresh fingerprint, no group identifier is ever used
twice.

\subsection{Tombstones}

Removing fragments is not enough. A gridnode that is offline during the delete comes back with its fragment, and
without a record of the delete, repair would count that fragment and, with enough of them, rebuild the group.
Gridnodes therefore keep the proof as a \emph{tombstone}. A tombstone lives for \code{tombstoneDays}, 30 by default,
counted from the moment each gridnode receives it. While it lives, the gridnode refuses new stores of that group and
hands the signed proof to any repairer that asks about it.

A holder that missed the delete learns of it at its next duty visit or relocation check (Section~\ref{sec:repair}).
Its census meets a tombstone, it verifies the proof against the key in its own descriptor, keeps the proof as its
own tombstone with a fresh lifetime, and drops its fragment. Every rank is on duty once every $W$ epochs
(Section~\ref{sec:repair}), so with the defaults a stale holder drops its fragment within about 40 hours. A claimed
tombstone without a valid proof is ignored.

\subsection{Consequences}

\begin{itemize}
	\item A lost fingerprint means a lost file. There is no recovery path, and the file's fragments stay stored,
	      because nothing expires.
	\item Sharing a fingerprint shares full ownership, delete included. The format has no read-only rights.
	\item Storage is charged to each gridnode's own quota, not to an owner. There is no payment or per-owner limit.
\end{itemize}

\section{Self-healing}
\label{sec:repair}

Gridnodes restore every group to full strength once its losses reach a threshold, without the owner and without
learning anything beyond single chunks. Repair is lazy for a reason: many losses are transient. A gridnode that
restarts, or loses its connection for an hour, comes back with its fragments, and rebuilding them at once would spend
bandwidth on data that returns by itself. Studies of peer-to-peer storage show that waiting until losses pass a
threshold saves much of that bandwidth, as long as the remaining redundancy covers the
wait~\cite{bhagwan2004,chun2006,giroire2010}.

\subsection{Scheduling}

Time is divided into epochs of \code{repairIntervalMinutes}, 60 by default: $e = \lfloor t / \mathit{interval}
\rfloor$. A gridnode starts repairing only once two epoch boundaries have passed since it first saw a valid spork,
which leaves at least one full interval for its view of the network to settle. In each epoch exactly one rank of a
group's window is on duty:
\begin{equation}
	\mathit{duty}(g, e) = \left(e + \mathit{prefix}_{32}(g)\right) \bmod \left(n_{max}(g) +
	\mathit{placementSlack}\right)
\end{equation}
where $\mathit{prefix}_{32}(g)$ is the first four bytes of the group identifier as an unsigned integer,
$n_{max}(g)$ comes from the group's own descriptor, and the slack from the current spork.

A gridnode acts only for groups it holds. If the gridnode at the duty rank holds the group, it makes a \emph{duty
visit} to the group. If the rank is a spare, or its gridnode has lost the fragment, nobody checks the group in that
epoch. Duty walks through the window one rank per epoch, so every holder is on duty once every $W$ epochs, 40 hours
with the defaults, and a group with $h$ holders gets $h$ visits in that time: with 24 holders in a window of 40,
about three epochs in five. One visit per group and epoch keeps the cost to $W - 1$ queries per group and epoch
instead of that many per holder. Each gridnode computes the duty from its own view of the active gridnodes, so
views that differ may give a group two visits in one epoch, or none. A gridnode that does not find itself in its
own view, as happens while that view fills in after a restart, leaves its groups alone for the round.

A holder whose rank has fallen outside the window checks in every round whether to relocate its fragment, whether
or not it is on duty (see \emph{Relocation} below).

\subsection{A duty visit}

Figure~\ref{fig:repair} shows the steps the gridnode on duty takes for one group.

\paragraph{Census.} The census asks every other member of the window whether it holds the group. A \code{HELD}
answer counts only with an index inside the group's slots, and a \code{TOMBSTONE} answer only when its delete proof
verifies and its public key equals the key in the local descriptor. A \code{NONE} answer marks a free rank. Any
other answer, and silence, count as nothing.

\paragraph{Lazy threshold.} Repair starts when losses pass a share of the parity budget:
\begin{equation}
	n_{in} - \mathit{present} \ \ge\ T = \max\left(1,\ \left\lceil m_{in} \cdot \mathit{repairThresholdPercent} / 100
	\right\rceil\right)
\end{equation}
where $\mathit{present}$ counts distinct indices, the duty holder's own and extras included. With the defaults
$T = 4$: repair starts once the distinct fragments of a group fall to 20, four more than the 16 it needs. Without
extras that means 4 of the 24 guaranteed fragments are missing; with all 8 extras held, it takes 12 losses.

\paragraph{Rebuild.} The repairer fetches the fragment of every claimant in parallel and keeps only those that verify
with the index they claimed. From any $k_{in}$ of them it decodes the chunk, re-encodes every missing index up to
$n_{max}$, extras included, and checks that the rebuilt tree has the signed root. The rebuilt fragments go out in
ascending index order, each to the next window member in rank order that answered \code{NONE} and accepts it. The
guaranteed fragments thus come first, and extras fill whatever room is left. The repairer needs no key for any of
this, because the signed root proves the rebuilt fragments genuine.

\paragraph{Spot checks.} A gridnode could claim to hold a fragment it has dropped and so delay repair. Duty passes
through the whole window once every $W$ epochs, and during one such rotation in four, every duty visit that finds the
group above its threshold also checks one claim. The duty holder picks one claimant with a secure random generator
and fetches its fragment. A claim that does not verify is dropped for this visit, and repair starts if the group then
falls to its threshold. Each holder thus checks on every fourth of its own duty visits. A spot check moves a whole
fragment, where a census answer is a few bytes, so checking a quarter of the visits keeps the cost low. Knowing the
schedule does not help a liar: answering \code{NONE} in a checked rotation only makes the loss visible.

Each liar adds one index to $\mathit{present}$ that is not really there. With $L$ colluding liars, repair therefore
starts for certain only when real losses reach $T + L$, or $T + L - 1$ in a visit whose spot check happens to pick
a liar. The inner parity must outnumber the liars that a window can hold. With the defaults and no extras, repair
still starts in time with up to four liars and needs a lucky spot check with five. With six liars and three honest
losses, a group passes its 8 tolerated losses before repair can start, whether or not a spot check catches one of
the liars.

\paragraph{Relocation.} A holder whose rank has dropped out of the window first runs a census, so a deleted group is
never moved. It then offers the fragment to free window members one by one. A member counts only after it stores the
fragment and serves back a verified copy with the same index; only then does the holder remove its own copy.

\paragraph{Growth limits.} A gridnode accepts fragment sizes between 1/16 and 16 times the current spork value, and a
repairer rebuilds only groups whose full size is at most $\min(\mathit{maxBytesPerNode},\ 16 \cdot n_{max} \cdot
\mathit{fragmentSize})$ under the current spork, 32\,MiB with the defaults. These limits stop old or malicious
descriptors from making gridnodes allocate unbounded memory. A repairer that skips a group for this reason logs a
warning, because a group that no holder may repair slowly decays.

\subsection{What a repairer learns}

During a rebuild the repairer holds the ciphertext of one chunk and knows which gridnodes hold its fragments. It has
no key to decrypt the chunk. The identifiers of the file's other groups are unrelated to this one, so nothing leads
the repairer to them, apart from the content links of short stripes (Section~\ref{sec:security}).

\section{Extra-parity pool and quotas}
\label{sec:quotas}

Each gridnode's store has two tiers, and idle disk space adds durability without ever displacing guaranteed data.

\begin{description}
	\item[Guaranteed] Fragments with index below $n_{in}$. They may use the whole quota, \code{maxBytesPerNode},
	      10\,GiB by default.
	\item[Extra] Fragments with index $n_{in}$ and above. They may use at most \code{extraPoolPercent} of the quota,
	      20\,\% or 2\,GiB by default.
\end{description}

When a guaranteed fragment needs room, the oldest extras are evicted first; only when no extras are left is the store
refused with \code{QUOTA}. A new extra that finds the pool full evicts older extras in the same way. Every entry is
charged at least 4\,KiB, so tiny fragments cannot exhaust the file system: a 10\,GiB node holds at most
2\,621\,440 entries, and about 163\,000 guaranteed fragments at default settings.

Tombstones cost 4\,KiB of quota each. A gridnode always tombstones a group it holds, since dropping the fragment frees
more room than the tombstone takes. It tombstones a group it does not hold only while all its tombstones together
stay within 1\,\% of its quota, about 26\,000 with the defaults, and while the quota has room, which may evict extras.
This bounds delete traffic for made-up groups, which costs an attacker only a fresh key per group. Every node, gridnode
or not, purges expired tombstones at the end of every repair round.

\paragraph{On disk.} Fragments live under \code{fragments/ab/cd/<groupId>.frag} in the node's data directory, one file
per group, behind a 12-byte header of format, slot count, tier, index and a 64-bit sequence number that orders
eviction. Tombstones live under \code{fragments/tombstones/<groupId>} as 112 bytes: expiry, the delete timestamp,
the public key and the signature. Every write goes to a temporary file first and is renamed into place atomically.
The file is not forced to disk, so a power cut can lose or damage the latest writes; the checks on every read catch
damage, and repair restores what is lost. At startup the store rebuilds its accounting by scanning these files:
malformed files are removed, files that cannot be read are skipped, and files of an unknown format are left in
place.

\subsection{Changing parameters safely}

Because every file keeps its own layout, most changes are safe at any time. Three need care:

\begin{itemize}
	\item \textbf{Sizes.} Gridnodes store fragments only within a factor of 16 of the current fragment size, and
	      rebuild only groups up to 16 times the current full group size. A change beyond these factors leaves older
	      groups with no gridnode that stores or rebuilds them, and they decay. Sizes should therefore move in
	      smaller steps.
	\item \textbf{The frame limit.} Validation does not tie the fragment size to the 256\,MiB frame limit of the
	      transport (Section~\ref{sec:protocol}), so a spork can name fragments too large to send.
	\item \textbf{Manifest copies.} The copy count is the cheapest lever on durability
	      (Section~\ref{sec:durability}), but like every layout value it applies only to new uploads.
\end{itemize}

\section{Network protocol}
\label{sec:protocol}

Storage traffic uses Hedgehog's existing peer-to-peer transport: Netty~\cite{netty} over QUIC~\cite{rfc9000}, which
encrypts every connection with TLS~\cite{rfc9001}. Peers do not authenticate each other yet: each server presents a
fresh self-signed certificate and each client accepts any certificate, so the encryption stops passive observers
but not an attacker on the path (Section~\ref{sec:security}). Storage requests travel over the node's existing peer
connections, and a window member without one counts as unreachable. Requests to the node itself are served
in-process. Each message starts with an 8-byte frame header (Figure~\ref{fig:frame}), and frames, header included,

never sits in a window and never repairs.

\subsection{Threading}

Replies arrive on Netty event loops, so the operations that wait for replies never run on one. Uploads, downloads
and deletes run on the REST server's worker threads, repair runs on a thread of its own, and delayed sends run on a
shared thread pool. Incoming requests are served on the event loops themselves, fragment verification and disk
access included.

\label{sec:analysis}

\subsection{Durability}
\label{sec:durability}

that holds $n$ fragments and needs $k$ of them is then lost with probability
\begin{equation}
	P_{\mathit{group}}(q) = \sum_{j = n - k + 1}^{n} \binom{n}{j} q^j (1 - q)^{n - j} ,

Four observations follow:

\begin{itemize}
	\item \textbf{The layers multiply their protection.} At $q = 10\,\%$ a group is lost with probability
	      $3.2 \times 10^{-4}$, but a full stripe only with $1.7 \times 10^{-47}$. Three replicas of every chunk
	      cost more and lose the same stripe with probability $3.2 \times 10^{-2}$.
	\item \textbf{Repair must act well before a third of the fragments are gone.} Near $q = 30\,\%$ groups fail
	      often and the outer code can no longer make up for it. Held extras push that point much further.
	\item \textbf{A file is only as durable as its weakest structure.} That is the manifest set, or a short last
	      stripe where the file has one. At $q = 10\,\%$ a last stripe of up to four data chunks is weaker than the
	      manifest set, and one of a single chunk, as in every file of at most one chunk and in the 32\,MiB and
	      1\,GiB files of Section~\ref{sec:overhead}, is weaker by more than three orders of magnitude. The last
	      stripe of a 100\,MiB file holds five chunks, so its manifest set dominates: the file is lost with
	      probability $3.4 \times 10^{-11}$, almost all of it from the manifest set. More copies help most: five
	      manifest copies lower the manifest's loss at $q = 10\,\%$ from $3.3 \times 10^{-11}$ to $3.4 \times
	      10^{-18}$, for the price of two more groups per file.
	\item \textbf{The same numbers bound a coalition.} A coalition that runs a share $q$ of the gridnodes, spread
	      over the windows by rendezvous hashing, destroys by dropping all its fragments at once what the table
	      predicts for loss probability $q$. For networks much larger than a window, the binomial model is a close
	      approximation of this case.
\end{itemize}

These numbers follow from the independence assumption, not from field data, and they cover one interval between
repairs. Real failures are correlated: machines in one data centre, on one power feed or running one software
version fail together~\cite{ford2010,nath2006}, and simple reliability models can mislead by orders of
magnitude~\cite{greenan2010}. Random placement spreads the groups of all files over all gridnodes, so a large
correlated failure touches a great many groups at once, and the chance that one of them loses too much grows with
their number~\cite{cidon2013}. Rendezvous hashing cannot see which gridnodes share a fate.
Repair also renews only the inner code (Section~\ref{sec:security}), so over a file's life every group that is lost
stays lost, and the outer margin of its stripe shrinks.

\subsection{Storage overhead}
\label{sec:overhead}

At default settings a large file costs about 2.26 times its size across the network, and a file of 1\,GiB 2.27
times. Small files cost far more, because every file carries three manifest groups and at least one data and one
parity chunk.

Each group stores 24 guaranteed fragments of 64\,KiB, 1.5 times the chunk. Each fragment also carries 302 bytes of
proof material: the 136-byte descriptor, 2 bytes of index and proof length, a 160-byte Merkle proof and a 4-byte
length. A file needs $D + \sum_s m_s + \mathit{manifestCopies}$ groups.

\subsection{Performance}
\label{sec:performance}

\paragraph{Computation.} Encoding costs one table lookup and one XOR per data byte for each parity row: 16 rows per
chunk for the inner code, which seals all 32 slots at once, and up to 16 rows per stripe for the outer code. Decoding
inverts a $k \times k$ matrix, at most $32 \times 32$, then recomputes every data shard from $k$ surviving shards,
even the shards that arrived intact, and re-encodes all parity. Its cost is therefore the same whether one shard or
eight are missing, two to three times that of encoding. Retrieval skips the outer decode when every data chunk
arrived, but it always runs the inner decode. AES-GCM runs in hardware on processors with AES instructions. Hashing
adds one SHA-256 pass over each fragment for its Merkle leaf.

\paragraph{Memory.} An upload or download holds one stripe at a time: up to 32 pieces of plaintext beside the 48
chunks of 1\,MiB, about 80\,MiB, plus the fragments of the group being sealed or decoded. Memory therefore does not
grow with file size, but it does grow with the number of concurrent requests.

\paragraph{Bandwidth and latency.}

\begin{itemize}
	\item \textbf{Store} sends every fragment once: about 2.27 times the file for the guaranteed fragments, and
	      about 3.02 times with the extras, which gridnodes keep in their extra pool, evicting older extras when it
	      is full. Groups are placed one after
	      another, each waiting for its slowest guaranteed store, so a store costs at least one round trip per group
	      and up to 25\,ms of delay; for a 64\,MiB file, whose 101 groups each wait for the longest of 24 random
	      delays, that adds about 2.5\,s.
	\item \textbf{Retrieve} reads 18 fragments for each 16 it needs, about 1.13 times the file when no chunk is lost.
	      Groups are fetched one after another, and parity groups only for stripes with a missing data group.
	\item \textbf{Repair} reads all surviving fragments of a group, about 20 at the threshold, to rebuild the
	      missing ones. Its cost is proportional to what was lost, not to the file.
	\item \textbf{Census} sends $W - 1$ small queries per group and duty visit. A full 10\,GiB node is on duty for
	      about one fortieth of its groups per epoch: roughly 4\,000 censuses an hour, which make 160\,000 queries
	      and as many replies. It answers about as many queries from other gridnodes.
\end{itemize}

Three improvements would raise these figures without any change to the format: split-table or vector
$\mathrm{GF}(2^8)$ multiplication~\cite{plank2013,isal}, a decode path that skips the work when all data shards are
present, and placing and fetching several groups at once.

\section{Security analysis and known limits}
\label{sec:security}

The design meets its goals against the parties of Table~\ref{tab:threats}, with the following limits.

\begin{description}
	\item[Linked groups] Outer parity is a fixed linear combination of the stripe's data chunks with public
	      coefficients, and the inner code is linear too. The fragments of a stripe's groups therefore satisfy the
	      outer code's equations, index by index. For a stripe with one data chunk the equation is equality: the
	      Cauchy coefficient for $k = 1$ is 1, so the parity chunk is a copy of the data chunk, the two groups have
	      identical fragments and the same Merkle root, and anyone who sees both descriptors can link them. This
	      covers every file of at most one chunk, and the last stripe of every file whose number of data chunks leaves
	      a remainder of one when divided by 32, such as the 32\,MiB and 1\,GiB files of
	      Section~\ref{sec:overhead}. For stripes of two or
	      three data chunks, an observer that collects same-index fragments of many groups can search for sets of
	      three or four groups that satisfy the equations. For full stripes of 32 chunks such a search is out of
	      reach. Encrypting each parity chunk under its own key would remove these links without changing what
	      gridnodes do.
	\item[Traffic order and timing] The traffic of one upload comes from one node in a short time. Within a stripe,
	      groups leave in shuffled order and fragments with random delays, but stripes follow one another and the
	      manifest copies always go last, in order. Reads and deletes are not shuffled at all: retrieval fetches the
	      data groups in index order, and a delete walks the file stripe by stripe and sends to every member of each
	      window. A gridnode may therefore guess that several of its fragments belong to one upload. In a network of
	      at most $W$ gridnodes, where every gridnode sits in every window, it can reconstruct a file's group list and
	      stripe structure from the deletes alone. It still learns no plaintext. Relay routing~\cite{dingledine2004}
	      and shuffled reads and deletes would remove the link.
	\item[Unauthenticated transport] QUIC encrypts every connection, but peers do not authenticate each other yet.
	      An attacker on the network path can intercept a connection and see what a curious gridnode would see:
	      fragments, descriptors and the timing of requests. It gains no key, and forged fragments still fail
	      verification.
	\item[Small files] Uniform chunks cost space: a 1\,KiB file occupies five groups. This is the price of groups
	      that all look alike. Small files are also the least durable, because their only stripe is short
	      (Section~\ref{sec:durability}).
	\item[Lost groups stay lost] Repair renews only the inner code. A group that falls below $k_{in}$ fragments is
	      gone for good: retrieval rebuilds its chunk in memory from the outer code but stores nothing. The outer
	      margin of a stripe is therefore spent, never renewed, over the life of the file.
	\item[No expiry] Nothing expires. The groups of an upload that crashed before its rollback, and the groups of
	      files whose fingerprint was lost, stay stored, repaired and charged to quota for as long as the network
	      runs.
	\item[No payment] The only abuse limit is each gridnode's quota. Payment and anti-spam are not part of this
	      layer.
	\item[Resurrection] A tombstone expires after \code{tombstoneDays}. A deleted group could come back only if at
	      least $k_{in}$ holders that missed the delete returned after every tombstone had expired, and the file would
	      stay unreadable unless a manifest copy returned the same way. A delete withdraws the manifest copies from
	      the data window, so a copy that only the wide search finds may escape it.
	\item[Retrievability] Spot checks prove that a claimant can serve a fragment when asked, not that it stores it:
	      it could fetch the fragment from another holder on demand. Proofs of data possession~\cite{ateniese2007}
	      and of retrievability~\cite{juels2007} check storage with less data moved, and proofs of
	      replication~\cite{filecoin2017} also make it costly to answer from someone else's copy.
	\item[Liars] Colluding gridnodes that falsely claim fragments can delay repair, bounded as described in
	      Section~\ref{sec:repair}.
	\item[Coalitions] An attacker that runs a large share of the gridnodes holds a similar share of every window.
	      By dropping its fragments at once it causes the losses of Table~\ref{tab:loss}, with $q$ equal to its share:
	      a fifth of the gridnodes already threatens small files and manifests. Collateral makes gridnodes expensive
	      to run and so limits Sybil attacks~\cite{douceur2002}; the storage layer relies on it and on the list of
	      active gridnodes.
	\item[Eclipse] Placement trusts each node's view of the active gridnodes. An attacker that controls that view,
	      as in an eclipse attack~\cite{singh2006}, could steer a node's uploads to its own gridnodes.
	      Announcements of gridnodes are signed with the gridnode's own key and expire after thirty minutes
	      without a fresh signature, so a peer can neither forge nor revive an entry; it can still withhold
	      entries from a node whose connections it controls. Nothing yet ties a key to collateral, so anyone
	      can announce as many gridnodes as they like.
	\item[Spork key] The holder of the foundation's spork key can stop new uploads, disable storage with a spork
	      that fails validation, or set sizes under which old groups can no longer be stored or rebuilt
	      (Section~\ref{sec:governance}). It cannot read, find or delete a file.
	\item[Tombstones on plain nodes] Any Hedgehog node that receives a valid delete keeps the tombstone until it
	      expires, bounded by its tombstone budget, although a node that sits in no window has no use for it.
\end{description}

\section{Related work}
\label{sec:related}

\paragraph{Peer-to-peer storage.} PAST~\cite{rowstron2001} and CFS~\cite{dabek2001} replicate files or blocks over
distributed hash tables. OceanStore~\cite{kubiatowicz2000} archives data as erasure-coded fragments, each made
self-verifying by a hash tree whose root names the object, and reads by asking for more fragments than it needs.
Glacier~\cite{haeberlen2005} adds massive redundancy to survive correlated failures. Work on availability
management shows that bandwidth, not disk space, limits storage on churning peers~\cite{blake2003}, and that lazy
repair with a threshold saves much of that bandwidth~\cite{bhagwan2004,chun2006,giroire2010}. Hedgehog's lazy
threshold and its pool of extra parity follow these lessons.

\paragraph{Anonymous storage.} Freenet~\cite{clarke2001} and Free Haven~\cite{dingledine2000} aim to hide who
publishes and who reads what. Hedgehog's goal is narrower: it hides what the pieces contain and which pieces form a
file, but not which node sends a request (Section~\ref{sec:security}).

\paragraph{Decentralized storage networks.} Tahoe-LAFS~\cite{wilcox2008} encrypts and erasure-codes files on the
client and hands out capabilities that combine the key with the location; checking and repair are left to clients
that hold a capability for the file. Storj~\cite{storj2018} spreads Reed-Solomon pieces of encrypted segments over
untrusted storage nodes, and derives piece identifiers so that storage nodes cannot tell which pieces belong
together. Its satellites, coordinators that hold the metadata of the files they manage, audit the nodes and repair
lost pieces.
Sia~\cite{sia2014} lets clients store erasure-coded pieces with hosts under contracts on its blockchain, and leaves
the upkeep of each file to its client. IPFS~\cite{benet2014} names content by its hash and leaves redundancy to
whoever keeps a copy, and Filecoin~\cite{filecoin2017} adds payment and proofs that storage providers keep distinct
replicas over time. Swarm~\cite{swarm2024} erasure-codes the chunks of its hash trees and stores replicas of root
chunks at addresses derived from the root. What Hedgehog adds is erasure-coded repair by the network itself,
without the owner or a coordinator, while the structure that ties chunks into files stays with the owner.

\paragraph{Secure dispersal.} Rabin's information dispersal~\cite{rabin1989} splits data into pieces of which any
$k$ rebuild it. Krawczyk's secret sharing made short~\cite{krawczyk1993} and AONT-RS~\cite{resch2011} combine
encryption with dispersal, so that fewer than $k$ pieces reveal nothing. Hedgehog also encrypts before it disperses,
but it keeps the key out of the network.

\paragraph{Codes for storage.} Regenerating codes~\cite{dimakis2010} cut the bandwidth of repair, and local
reconstruction codes~\cite{huang2012} and the two-level scheme of f4~\cite{muralidhar2014} keep most repairs within a
small set of shards. Hedgehog's inner code plays that local role, for privacy as much as for cost.

\section{Future work}
\label{sec:future}

\begin{itemize}
	\item An object-storage layer with buckets and keys, in the style of S3, built on top of this layer.
	\item Breaking the linear links between the groups of a stripe, for example by encrypting outer parity chunks
	      under keys of their own, so that no group can be tied to another by its content.
	\item Renewing outer redundancy: a node that finds a lost group while reading a file could seal and store it
	      again.
	\item Relay routing of storage traffic~\cite{dingledine2004}, and shuffled order and random delays for reads and
	      deletes as well as uploads.
	\item Authenticating peers by their gridnode keys, and opening connections to window members on demand.
	\item Expiry or leases for groups, so that orphaned data does not stay stored forever.
	\item Batched census queries across groups, and backpressure in the transport.
	\item Moving fragment verification and disk access off the network event loops.
	\item Proof of collateral for a gridnode's key, so that a signed announcement also shows that the gridnode is
	      paid for.
	\item Faster field arithmetic, and codes with cheaper repair~\cite{dimakis2010}.
	\item Stronger storage challenges than spot checks~\cite{ateniese2007,juels2007}.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}

Hedgehog stores files on gridnodes that nobody needs to trust. One random fingerprint names, decrypts and controls a
file, and nothing else about the file is kept anywhere. Two layers of Reed-Solomon coding separate what the owner
knows from what the network needs: the owner's outer code spans many chunks and stays secret, while the public inner
code lets gridnodes check, repair and move each chunk on their own. Signed descriptors and Merkle proofs make every
fragment self-verifying, rendezvous hashing places fragments without a directory, and a signed spork tunes the
network while every file keeps the layout it was written with. The known limits are stated plainly in
Section~\ref{sec:security}: linked groups in short stripes, traffic that reveals structure, a transport without peer
authentication, and outer redundancy that is never renewed. Each has a remedy in Section~\ref{sec:future}, and the
format identifier lets the network adopt those that change stored structures beside the current format.

\section{Glossary}

\begin{description}
	\item[Census] The duty holder's query of every window member about one group.
	\item[Chunk] A fixed-size piece of AES-GCM ciphertext or outer parity.
	\item[Descriptor] The signed 136-byte header that describes a group and commits to its fragments.
	\item[Duty] The task of checking one group in one epoch, which falls to the holder at one rank.
	\item[Epoch] One repair interval, 60 minutes by default.
	\item[Extra fragment] A fragment beyond the guaranteed set, kept only while quota allows.
	\item[Fingerprint] The 32-byte secret that locates, decrypts and controls a file.
	\item[Fragment] One inner-code piece of a group, the unit a gridnode stores.
	\item[Gridnode] A service node that provides the network with storage, communication and compute.
	\item[Group] One chunk as the network sees it, named by the hash of its public key.
	\item[Guaranteed fragment] One of the first $n_{in}$ fragments of a group, which the upload places and repair
	      keeps.
	\item[Holder] A gridnode that stores a fragment of a group.
	\item[Manifest] The encrypted record of a file's size and layout.
	\item[Rank] A gridnode's position in a group's rendezvous ranking.
	\item[Spot check] A duty holder's check that one census claimant really serves its fragment.
	\item[StorageSpork] The signed spork that sets every storage parameter.
	\item[Stripe] Data chunks and their outer parity, known only to the owner.
	\item[Tombstone] A kept delete proof that blocks a group from being stored again.
	\item[Window] The $W$ highest-ranked gridnodes for a group.
\end{description}
